# Contributing

**Status:** [✓ final] · v1.2.0 · 12 July 2026

This is a single-author case study with an open door. Contributions improve it; they do not co-author it. One named human remains accountable for every claim in the repository, which is the repository practicing its own control C1 (`09-compensating-controls.md`).

## What is accepted

1. **Resolutions of open questions (Q-series).** Any item in `12-open-questions.md`, resolved against vendor documentation, direct vendor response or authoritative reporting. State the source; it will be tiered per the authority hierarchy in `01-abstract-and-method.md` and added to `13-sources.md`.
2. **Factual corrections.** A claim, the correction and a source. Corrections against higher-tier sources displace claims resting on lower tiers; the superseded claim is marked, not deleted.
3. **Enterprise questions (E-series).** Questions from real deployment experience, for `14-enterprise-question-set.md`, with a one-line "why it matters" and at least one possible resolution. The README calls these the most valuable contribution, and it means it.
4. **Sources.** Primary or higher-tier sources for claims currently resting on secondary ones, and prediction-relevant events for `11-predictions-register.md`.
5. **Counterarguments.** Objections to the analysis strong enough to join the stress-test set in `10-verdict.md`.

## What is not accepted

Style edits, unverifiable claims, vendor marketing restated as fact and product assertions that cannot be tied to documentation or reproducible research. Anonymous product claims are recorded, at most, as open questions.

## How

Open a GitHub Issue for anything substantive; pull requests are accepted for source additions and typographical corrections. Analytical changes are made by the maintainer so that authorship and accountability stay in one place. Corrections may be shared formally or informally, from the vendor or anywhere else; they are attributed only with the contributor's consent, and informal pointers are used to check the public record rather than quoted.

## What happens to an accepted change

Version bump, changelog entry and, where a prior claim is revised, a visible supersession mark. The update protocol in the README governs. Errors stay visible.
