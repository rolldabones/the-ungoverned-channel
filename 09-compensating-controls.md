# 09 · Compensating Controls: Conditions of Governability

**Status:** [✓ final] · v1.1.0 · 15 October 2026 (KST)

> **Re-check note, 15 October 2026 (KST).** C2, C3 and C7 are rebuilt against the vendor's data-lifecycle and response-control pages read that day (`12` Q1, Q4, Q5 resolved); C11 is added so that ledger rows 10 and 11 have controls. The 8 September 2026 condition on C7 is discharged: what removal achieves is now documented, and it is nothing.

Each control is stated with its test, because a control that cannot be tested is a wish. Together these are the conditions under which the study's verdict (`10`) concedes governability. They correspond to ledger rows in `05`; every row 1 to 11 now maps to at least one control.

**C1. Named owner per channel** (ledger row 1). One accountable human is designated for each channel the agent joins; that person owns every agent output in the channel regardless of who tagged it, and ownership is recorded where the organization records accountability, not in a wiki no one reads. *Test:* for any sampled agent output, the responsible human can be named within one business day. Restores **Final Liability** by policy where the product does not supply it.

**C2. Ambient mode off** (row 4) at deployment, enabled only channel by channel on a documented risk assessment signed by the channel owner. The vendor's setting is **Respond automatically**, on by default and per channel with no estate-wide switch, so C2 is executed once per channel. **Companion, added 15 October 2026:** **Channel member edits** set to Block for the workspace or all of Slack, because otherwise any channel member can turn the setting back on by asking Claude in the channel. *Test:* configuration audit shows Respond automatically off and member edits blocked everywhere an assessment does not exist. Restores **Informed Intent** in the only way currently possible: by declining the feature that negates it.

**C3. Channel admission screening** (rows 2, 3, 7, 11). Before the agent joins any channel: no counsel communications (see `08`), no channels carrying regulated personal data, MNPI or active-investigation material. The Slack Connect and guest limb is recast (15 October 2026): the vendor default already keeps Claude off in channels with guests and in Slack Connect channels, so the control is to **keep that default and audit every override** an Owner or Claude Tag admin makes, rather than to screen channels the agent cannot enter unaided. *Test:* admission checklist on file for every channel where the agent is present, and the guest and Slack Connect settings show no override without a signed assessment.

**C4. Connector minimalism** (row 5). Narrowest scopes supporting the approved use case; no email connector in shared channels; scope additions require the same approval as initial grant. *Test:* quarterly diff of granted scopes against approved use cases produces no unexplained entries.

**C5. Service-account treatment** (rows 1, 5). The agent identity is registered in the identity governance program: explicit owner, scoped permissions, quarterly access recertification, review of channel memberships in every joiner-mover-leaver cycle. *Test:* the agent appears in the same recertification reports as privileged human accounts.

**C6. Rehearsed Exit** (rows 2, 8). Before deployment, execute and time the full removal procedure: agent out of a channel, connectors revoked, integration terminated, and confirmation of what happens to channel memory at each step. If memory disposition on exit cannot be confirmed, this is a blocking finding, not a risk acceptance. *Test:* a dated runbook with measured elapsed times exists and is re-run semiannually. This is the **Exits** primitive doing its only job: an exit that has never been rehearsed is a diagram.

**C7. Memory hygiene by scope removal** (row 2). ~~Until enumeration and expiry tooling exists, time-bound accumulated context: periodic agent removal and re-admission on a schedule set per channel sensitivity.~~ **Struck 15 October 2026 (KST).** The vendor's data-lifecycle page states that `/remove @Claude` deletes nothing and that re-adding Claude restores memory, routines and sessions, so removal and re-admission never was a reset. The documented per-channel deletion is an Owner's **Remove this scope**, which deletes the channel's memory and with it every session and transcript recorded to that moment; the documented targeted correction is Owner deletion of entries in the memory-files view, which removes the entry from what Claude reads while earlier versions remain stored until the scope's data is deleted. C7 as rebuilt: scope removal on a schedule set per channel sensitivity, executed by an Owner, logged, and preceded by the preservation check in `08.B`, because the same action destroys the transcript a hold might require. Nothing expires on its own during the beta, so the schedule is the only clock. The cost is the product's convenience; convenience is the correct thing to spend. *Test:* scope-removal log per channel, each entry preceded by a recorded hold check.

**C8. Untrusted-input posture** (rows 6, 7). All channel content is treated as untrusted input to the agent. High-impact actions (merges to protected branches, external sends, record modifications, financial transactions) require human confirmation through a surface outside Slack. *Test:* attempt each high-impact action class in a controlled channel; confirm the out-of-band gate fires.

**C9. Ongoing classification function** (regulatory file `07`). A standing review, quarterly at minimum, of what channels actually use the agent for, mapped against EU Annex III categories, Korea's high-impact domains and applicable sectoral rules, with authority to remove the agent from drifted channels. *Test:* the review's output is a dated register naming channels, uses and classifications. This control has no vendor equivalent and no standard-catalogue equivalent yet; it is the study's principal original recommendation.

**C10. Deployer-side log custody** (row 9). Audit console output exported and retained under the deployer's retention schedule, with the reconstruction gap (memory state and non-determinism) documented in the risk register rather than discovered during an incident. *Test:* logs are producible for a sampled 90-day-old event.

**C11. Bundle provisioning as a privileged change** (rows 10, 11). Access bundles give the organizational agent its connections and credentials; a change to a bundle or to where it applies is a privileged change and goes through the same named approval as a production access grant, with every granted connection mapped to the named owner under C1 and the requesting human recorded in commit and pull-request bodies where code is produced. *Test:* every bundle change in the audit log has a matching approval record; a sample of merged pull requests authored by the Claude GitHub App names the requesting human in the body.

## The honest cost accounting

C2, C3, C4 and C7 collectively decline most of what the product's launch materials sell. That is not a defect of the controls; it is the measurement of the governance discount defined in `01`. An organization unwilling to pay it should not deploy; an organization told the discount is zero is being sold to.

Final Liability rests with the Human.
